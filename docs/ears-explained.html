EARS

A live-coded techno set in a terminal. The human writes SuperCollider patterns. Claude-powered DJs cannot hear and cannot touch the code: they read a measured listening report and propose small patches. The human takes or skips, every change lands on a bar line, and every message is on screen.

Every proposal has to predict what it will do to the sound, and the host grades that prediction two bars later. Over 392 graded ideas, agents given the report were right 46% of the time; from the code alone, 20%. How it was measured.

Architecture

Four processes, three boundaries

The TUI is a Node program drawn with Ink. It spawns sclang and talks to it over OSC on localhost, spawns short-lived claude -p processes for ideas, and publishes every message on a bus that three readers share.

Timing across the boundary

SuperCollider stamps each hit and bar with its logical clock and announces it s.latency (200 ms) before it sounds. UDP adds jitter, and jitter only ever adds, so engine.ts takes the smallest lateness seen recently as the clock offset (creeping up 0.2 ms per message so it can recover). Flashes and lanes fire on the hit, however late the packet was.

Separation of concerns, by file

engine.scd sound · engine.ts process + OSC · report.ts hearing · agent.ts prompt, validator, Claude call · patch.ts patch → code · skills.ts grants · djs.ts personas · seed.ts bases · audio.ts FFT · ascii.ts visuals · bus.ts wire · app.tsx screen and keys.

When the host asks

  • 4 bars after a new base, first round.
  • 2 bars after a take, 1 bar after a skip, 4 bars after a failed round.
  • a asks now; --manual turns the automatic asks off.
  • A note typed mid-round cancels the round and re-asks at once, with the note.

What goes in the prompt

  • Tempo, key and bass root.
  • All six slots as they are on disk.
  • The latest listening report, ranked worst-first.
  • A table of every metric and what actually moves it, because the benchmark showed good changes failing on the wrong name.
  • Your note, which outranks the report (only the DJ's Never list outranks it).
  • The last 8 verdicts: taken or skipped, with each idea's reason and how its prediction was graded.
Sensing

What the agent gets instead of ears

An ears synth on the master bus streams numbers 15 times a second, and each of the six slots plays to its own bus with its own analyser before the shared effects, so the host can also say which voice moved. Every 2 bars it averages them, compares each to a reference, and writes one plain word per line. That text is all it knows about the sound.

The setup

One DJ (THE RESIDENT), one idea per round, taken automatically, on a second muted engine. Four seeded bases are measured clean; that measurement is the target. Then each is damaged: the kick buried, the hats 2.6× too loud, the low voice's filter 3.2× open. The damage is folded into the numbers rather than appended as * 2.6, so the source is not an answer key and the code-only condition is really blind. Seven rounds per seed per condition. npm run ears:bench.

What is measured

Prediction. Every proposal carries EXPECT air down. Two bars later the host measures what moved and grades it HIT, MISS or FLAT. FLAT means the move was smaller than the noise floor, which is measured from four windows of the unchanged music rather than assumed.

Repair. Distance from the clean base, in tolerances: 1.5 dB per band, 0.15 octave of brightness, 1 dB of level. Two windows of the unchanged base sit about 1.1 apart, so 1.1 is roughly the resolution limit.

Three findings, now in the code

Finding 1 · fixation

The agent chases the loudest number

Given twelve measurements of equal weight, the DJ called air 11 times in 28 rounds. Loud hats are the largest number in the report, so it kept working on them while the buried kick stayed buried. Ranking the problems by distance from the target moved its top call to loudness, 12 of 28, which is where the damage was, and it repaired best.

Same numbers, different order. brief.ts

Finding 2 · timidity

Most failures are moves that are too small

Across 392 graded ideas, 2 moved the sound opposite to the prediction and 269 were FLAT: the right thing moved, by too little to measure. The report now states the measured noise floor in the units the call will be graded in, such as "a change to air smaller than 2.0 dB cannot be measured", and asks for a move big enough to register.

Floors are per metric and per slot. shots.ts

Finding 3 · brightness

Brightness calls are where it goes wrong

Seven of the eight MISSes across all four runs were a call of brightness down or high down. Closing a filter darkens that voice but often leaves the mix as bright as it was, because the other five voices did not move. A whole-mix analyser cannot see the difference, which is why each slot now plays to its own bus with its own analyser.

Six taps, before the shared effects. engine.scd · slotears.ts

Five things the flat table leaves out: which problem to fix first (clipping outranks a band, a band outranks a colour); which voice drifted, from the per-slot taps, against how the base started; which two voices fill one band at the same moments, which is usually what "muddy" means; how big a move has to be to register; and what this agent has already tried without effect. The last one is what stops the fixation in finding 1.

What this cannot tell you

  • Four seeds, one DJ, one model, 28 ideas per cell. Read the ordering, not the decimals.
  • Grading is observational on a live mix, not a controlled re-render. The per-slot figure rebuilds the dry mix with every other voice held at its "before" measurement. The edited voice still carries its own randomness, and shared effects sit outside it.
  • The step from ears + shots to brief + shots is not significant on its own (p = 0.25). The gap from code-only to the full protocol is (p = 0.003).
  • "Repair" means distance from a measurement of the clean base, not whether the music got better. None of it was heard.

Full write-up and every round of every run: docs/does-the-protocol-help.md and docs/bench/.

Containment

Five checks between the model and the speakers

The model never writes code. It writes a few lines of patch, the host builds the expression, and anything that fails becomes a rejected message rather than an option on screen.

# what the model returns (plain text, a few dozen tokens)
SLOT d4
SET cutoff = 600
SET res = 2.8
REMOVE pan
WHY one sentence, under 14 words
EVIDENCE the report line or style rule
# optional, only if the skill is granted
FOR 1            # fills
WITH build      # drops
# what the host builds and shows as a diff
~d.(\d4, \instrument, \bass, \dur, 1/4,
  \midinote, Pseq([...], inf),
  \cutoff, 600, \res, 2.8, \amp, 0.6)

# on the projector
cutoff 1500 → 600 · res 2.2 → 2.8 · − pan
  1. No tools. Claude runs as claude -p --tools "" --strict-mcp-config --setting-sources "" --no-session-persistence. No files, no shell, no MCP. It can only return text. It uses the Claude subscription, no API key.
  2. Patch parser. Lenient about fences and stray backslashes, strict about shape: needs a slot d1–d6, at least one SET, and a WHY. Otherwise: "not in patch form".
  3. Validator. The built code must start with ~d.(\dN for its own slot; contain none of unixCmd systemCmd File Pipe interpret compile thisProcess .load Quarks NetAddr Server s. SynthDef ; exit; have balanced brackets; and fit in 600 characters ("too long to read on a projector").
  4. Grants. A patch that uses FOR, WITH, \vox or ~v. without that skill active is refused. Duplicates of another option are refused.
  5. Verdict, then SuperCollider. Only a verdict writes the file. The engine interprets it inside try; on error it answers /evald 0, the bus carries error, the slot shows "still playing the last good version", and the old Pdef never stopped.

Your own saves skip steps 1 to 4 on purpose: the human is trusted, the engine still fails safe.

Autonomy

Takeover and skills are grants

The agent never learns a new message. Granting something changes how the host acts on its behalf. The grant goes on the wire, and you can take it back mid-set.

Takeover

o gives the active DJ auto; O gives it to everyone in the booth. Two bars after ideas appear, the host takes one for the DJ, rotating style → fix → bold, and rides a two-bar build into the bold ones. n vetoes inside the window. o again takes control back. Each such verdict is logged by: "grant:auto".

Skills

A DJ starts with the basic vocabulary and is not told the rest exists. Taken ideas unlock skills (unlock on the wire); the glyph under the face blinks k!; k activates it (grant {skill}), K gives any skill now. Activated skills persist as skills: in the DJ's markdown, so revoking is editing one line.

SkillUnlocks afterPatch syntaxWhat the host does
⟲ fills1 takeFOR 1 or FOR 2Keeps the patch that many bars, then rewrites the slot to what it was. The lane shows "fill · back in N bars".
♪ vocals2 takes\vox with buf = ~v.("work it")Renders the phrase with macOS say in that DJ's voice, loads the WAV into a buffer, waits for /voxd, only then evaluates the slot. chop, len, rate patterns make the hook.
▲ drops3 takesWITH build or WITH washRides a two-bar transition and writes the file about 450 ms before the bar line, so the change lands on the drop.

Asking a DJ for vocals, a fill or a drop in a note while the skill is locked gets an in-character refusal that says how many takes remain and points at K.

Personas

A DJ is a markdown file

Deliberately the shape of a Claude Code skill: frontmatter, then four headed sections. The Never list is what gives a DJ a personality, and the prompt treats it as absolute.

# Style    Half as many notes, twice as much room…
# Idioms   Hats quiet (amp under 0.12), \hp high…

# Greeting Shh. Listen to the room between the notes.

In the booth

  • Faces from parts. head, hair (7), eyes (6), headphones (3), rig (decks, laptop, modular). A generated DJ picks names from lists and never draws. They nod on the kick, open their mouth on the snare, and the cans flash on hats.
  • Summon. s plus a description has Claude write a persona against a JSON schema whose enums are the real palettes, looks and parts. It is saved, walks in on a riser with its own look and palette, and says its greeting (aloud with v).
  • Back to back. Up to three share the booth; after each verdict the next one steps up. tab skips ahead, x retires.
  • Tallies. Under each face: taken / offered, the slots currently theirs, and skill glyphs.

On disk now, ten: The Resident, Detroit 130, Dub Siren, Acid Reflux, DJ Tambor, Nightbus Nia, Heon, Queen Funty, Miss Bonbon, Velvet Scat.

Who wrote it

The slot id and lane take the author's colour: grey for the seed, white for your saves, the DJ's palette accent for a taken idea, with the bar it landed on. The host sets its own copy before writing, so the file watcher does not credit a DJ's change to you.

What just changed

Code is split into \key, value tokens. Tokens a change brought in glow in the accent for 8 bars. Keys recede, values stand out, and ~x.("X---x---") rows are redrawn as steps: X a full block, x a half block, anything else a dot.

What each take did

The ears pane charts loudness and brightness per report, with a ▴ in the author's colour wherever a change landed. A broken slot says so in place and keeps playing its last good version.

Sound

Seeded bases: a style first, then everything else

One number picks a style; the style decides the tempo range (even BPMs only), scale pool, kick figure, hat feel and swing, clap placement, what the bass does, the chord voice and the lead. A four-bar progression is chosen from six, and the bass follows it with \ctranspose, Pseq([0, -4, 3, -2], inf).stutter(16). Drum rows come as lists of four (A A A B), so grooves turn around every fourth bar, and patterns carry Pwhite, Pbrown, Pwrand, so one seed never loops identically. g rolls a new base through a build or wash; the previous set is archived to tui/sets/ first. b picks which family the next roll comes from — dark, vibey or anything.

Signal path, and why it is guarded

Transitions ride the mixer to a bar line

Visuals

Visuals: a shader that draws into text

Every cell gets a 24-bit colour from a cosine palette. Looks and palettes are chosen by name, so a DJ can bring one but never writes drawing code.

Real audio, not envelopes

A scope synth low-passes the master at 5.5 kHz and writes it into a 512-frame ring buffer at a quarter of the sample rate: 43 ms at 48 kHz. The TUI fetches it 20 times a second and runs its own 512-point FFT into 32 log bands (audio.ts). orbit, ring, terrain and waterfall draw that signal.

Ten looks

Field (per-cell functions): gyroid, torus, warp, moire. Braille (2×4 dots per cell): wire, terrain, orbit, ring. Glyph: codefield tiles your live code and lights it; waterfall is a scrolling spectrogram. A pulse of kick / snare / hat / stab envelopes, bar phase and the five bands drives motion.

Pixel mode

The default character mode. Each cell is a ▀ whose foreground is one sample and whose background is the sample below, so field looks render at twice the vertical resolution as colour. c cycles pixels, ascii, blocks, dots, code.

Change on screen = change in sound

When a slot lands, the field wipes to a new look and palette on that bar (iris, blinds, sweep or shatter, at most every 2 bars). A DJ walking in, a new seed or a granted skill puts a name in lights: cfonts block letters that assemble from static and dissolve, one of six fonts per DJ, narrower ones tried if it will not fit.

Palettes also theme the interface: two accents each over shared neutrals #e8e6f0 / #8a8799 / #3d3b4a, so a transition recolours the whole screen.

Protocol

The wire

Everything between host, agents and human is one JSON line with the envelope v, t, bar, type, from. The log pane (e), tui/logs/latest.jsonl and the socket on localhost:57400 read the same stream. It is the proof that nothing reaches the speakers without validation and a verdict.

The messages are the EARS protocol (ears-protocol/SPEC.md, v0), which has its own page. Its claim is wider than music: host, agent, human; the agent observes and proposes, the human decides, the host is the only thing that changes the work. Honesty

What is verified, and what is not

The assistant that built this cannot hear. Everything under "verified" was checked by measurement on a second, muted engine with its own ports and set folder. Nothing on this page claims the music is any good.

Verified by measurement, muted

  • Engine boots headless; slots evaluate and hot-swap on the bar.
  • Broken code is refused while the music continues.
  • Measurements and hit times arrive; the report renders.
  • Claude returns valid patches; a take lands; a typed note changes the next ideas.
  • Round timings: the example session shows ideas 3.5 to 5.0 s after the ask; 392 benchmark ideas average 3.7 to 5.6 s.
  • Quit leaves no scsynth behind.
  • The master-chain fault was found by its numbers (limiter pinned) and fixed by design.
  • That the report helps: four runs, 392 graded ideas, same DJ, same damage, four conditions. The numbers.
  • Per-slot grading, by unit test: a louder hat raises air on its own tap while the other five voices are held still.

Not verified

  • How any of it sounds through speakers. Its builder has never heard a note.
  • Audio-to-visual latency by eye.
  • The tmux stage script with a real editor.
  • Whether "thin", "boomy" and the ±3 dB thresholds match what a listener would say.
  • Whether the reference profile is a mix worth steering toward.

Known gaps, from reading the code

  • The validator is a deny-list plus shape checks. It does not check instrument or argument names; an unknown one gets past it and is left for SuperCollider to refuse or ignore. A patch such as amp = 0 passes everything and produces silence.
  • Vocals depend on macOS say; if rendering fails the slot plays a silent buffer.
  • density and punch have no per-slot measurement, so a call on either is still graded on the whole mix.
  • The protocol's observe level is not implemented in this host; the levels that exist are suggest and auto.
  • The ranked report beat the flat one on four seeds. Four seeds is not many, and the gap to ears + shots alone is inside the noise (p = 0.25).
  • The engine ran at 24 kHz for part of the earlier work, which compresses the air band; everything quoted here is from 48 kHz runs.

Closed since the last version of this page: evidence.ts is wired into the screen, so "what did this take do" is computed rather than eyeballed off the trend chart; the log pane prints skill grants properly; a busy port 57400 now says so on the bus instead of failing quietly; the spec's music profile says six slots.

Usage

Run it

npm run ears:stage            # tmux: $EDITOR left, EARS right: the projector layout
npm run ears                  # just the TUI; edit tui/set/*.scd in any editor
npm run ears -- --seed 4821   # replay a base (the seed is in the header)
npm run ears -- --keep        # continue the set on disk instead of rolling a base
npm run ears -- --mute        # silent: the ears still measure
npm run ears -- --manual      # DJs only speak when you press a
npm run ears -- --demo        # visuals only, fake pulse, no SuperCollider
npm run ears -- --logs        # start with the wire pane open (also --full, --voice)
npm run ears -- --mood dark   # which family g rolls from: vibey (default), dark, any
npm run ears:tail             # follow tui/logs/latest.jsonl in another pane
npm run ears:ref              # record the reference, muted
npm run ears:reset            # restore tui/set from tui/set.start
npm run ears:bench -- 4 7     # the experiment: 4 seeds × 7 rounds × 4 conditions, its own muted engine
npm run test:ears             # 28 host tests: grading, noise floors, per-slot attribution, masking

Environment: EARS_MODEL (default sonnet), EARS_EFFORT (default low), EARS_ANGLES, EARS_SET, EARS_DJS, EARS_PORT 57200, EARS_SC_PORT, EARS_BUS_PORT 57400. The last five are how a second, muted test instance runs beside a live one without touching it.

Before EARS

The step before: choosing an engine by ear

soundcheck began as one brief (Detroit techno, 130 BPM, F minor) played by Strudel, Tone.js, Faust, Glicol and a SuperCollider render, level-matched, keys 1 to 5, so the stack would be chosen by listening instead of by reading docs. DECISION.md recommended Strudel for the date, with a Faust or Tone rack as the upgrade, and called SuperCollider the highest ceiling and the highest venue risk. EARS is what happened when the ceiling won: SuperCollider direct, in a terminal, with the agent moved from author to advisor. That document carries the same caveat as this page: verified for signal, levels and errors; never heard by the one who wrote it.
